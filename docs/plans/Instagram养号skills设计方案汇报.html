兼容插件机制底座与非插件机制底座

兼容性的关键不是让所有底座都理解 Cordis，而是把业务 skill、provider client、MCP connector 和未来 protocol 层拆成可替换边界。

底座类型 可用路线 当前状态 说明
支持插件机制的 TS agent instagram + ctx.instagram + provider 可设计落地 通过 Cordis 声明上下文服务，agent 服务读取 skill 计划后调用 provider。
无插件机制的 TS / Node agent 普通 InstagramClient 或 HTTP provider 可复用 client 不加载 Cordis；provider 主入口只导出 client/config/types。
支持 MCP 的 Python agent instagram-connector MCP Server 可直接连接 MCP 是协议边界，不要求 Python agent 支持 Cordis 插件机制。
Python agent 使用 API provider 未来 instagram-protocol + HTTP/MCP 服务适配层 存在缺口 当前 instagram-core 是 TS 类型包，Python 不能直接复用，需要用 OpenAPI/JSON Schema 固化协议。

职责边界：skill 提供计划，agent 决定执行

业务 skill 不直接操作 Instagram，也不替 agent 做 provider 选择。它输出可审计的计划和参数草案，执行结果由 agent 服务回写。

业务 skill

  • 理解目标与账号阶段
  • 生成计划、内容、决策
  • 输出工具参数草案
  • 汇总真实执行日志

agent 服务

  • 选择执行路线和 provider
  • 解析 sessionRef
  • 调用 API client 或 MCP tool
  • 处理循环、等待、超时、中断、重试

provider / connector

  • 执行真实 Instagram 能力
  • 校验 provider 专属限制
  • 返回结构化成功、失败或降级结果
  • 不承载业务编排

分层结构

分层的目标是隔离变化：业务规则、底座适配、通用接口和具体执行 provider 各自独立演进。

业务 skill/tool 层
instagram-warmup-orchestrator总编排，生成今日养号计划
instagram-profile-setup生成资料方案和编辑计划
instagram-video-interaction生成互动计划、判断和评论
instagram-content-publish生成草稿、发布计划、状态查询计划
底座适配层
instagram声明 Cordis ctx.instagram
通用能力接口层
instagram-core定义接口、类型、branded id 构造函数
provider/client 实现层
instagram-aiograpi-rest第一期 API provider
instagram-official-api官方 API 预留路线
instagram-connectorMCP 移动端操作兜底

两条执行路线

API provider 路线覆盖资料和发布的第一期主路径；MCP connector 路线先覆盖视频互动，也作为 API 不可用时的兜底执行方式。

API provider 路线

1

业务 skill 输出计划

资料编辑计划、发布计划、状态查询计划。

2

agent 服务读取计划

选择 provider，解析 sessionRef，补齐执行参数。

3

instagram-core 统一接口

TS 执行层通过类型和 client 契约约束请求。

4

provider 执行

instagram-aiograpi-rest 或后续 instagram-official-api。

MCP connector 路线

1

互动 skill 输出计划和判断规则

关键词、互动上限、停留时间、评论风格。

2

agent 服务执行循环

半小时 runner、等待和中断都由 agent 服务负责。

3

调用 MCP tools

搜索、采集、点赞、评论、下一条由 connector 暴露。

4

回传日志并汇总

skill 只汇总真实执行日志，不伪造动作结果。

sessionRef：统一但不固定结构

sessionRef 必要性来自 provider 差异：aiograpi-rest、官方 API、移动端 runtime 对登录态的真实需求完全不同，业务 skill 不应该理解这些内部结构。

sessionRef 稳定、不含敏感信息、对业务 skill 只是 string
SQLite registry 根据 sessionRef 找到 account、provider、session 类型和状态。
provider 专属表 每个 provider 保存自己的真实字段，避免把差异泄漏给业务层。
aiograpi-rest 解析为 aiograpi session id 和服务地址。
official-api 解析为 access token、IG user id、scope、过期时间。
connector 解析为 ADB serial、runtime host、artifact dir。

为什么需要

同一个账号可能走不同 provider；统一引用能让 skill 输出稳定，执行层按需解析。

安全边界

sessionRef 不包含 token、cookie、密码或 ADB 细节，日志也只记录引用和解析状态。

扩展方式

第一版用 SQLite，后续迁移到 Postgres、Secret Manager 或远端 session 服务时保持接口稳定。

connector 兜底策略

移动端操作优先使用 XML 组件节点，因为它更可解释、更稳定；截图坐标只在 XML 失败后单次兜底。

1

XML 快照

通过 UI XML selector 定位目标节点。

2

有限次重试

节点定位或点击失败时重试，记录 attempts。

3

截图坐标一次

调用模型或坐标识别服务推测点击位置，只执行一次。

4

降级结果

仍失败则返回 DEGRADED 和原因，不继续循环尝试。

结构化日志、benchmark 与 agent eval

计划型 skill 的价值不只是“不执行”，还在于把 agent 的决策链路变成可记录、可回放、可评分的数据。

计划字段稳定

每个计划包含目标动作、目标工具、参数草案、审批状态和日志字段，便于跨 provider 对比。

执行结果真实

skill 不伪造发布、点赞、评论结果；agent 服务写入 provider 或 MCP tool 返回的真实状态。

评测路径清晰

benchmark 可检查计划是否合理，agent eval 可检查 agent 是否按计划选择工具、处理失败并记录结果。

推荐开发顺序

先稳定接口和执行通道，再实现业务 skill，最后接入总编排和官方 API 后续路线。

P0instagram-core公共接口和类型先稳定。
P1instagram接入 deepseek-harness，注入 ctx.instagram。
P2instagram-aiograpi-rest资料和发布路线的第一期 provider。
P3instagram-connector视频互动依赖 MCP 移动端能力。
P4instagram-video-interaction在 connector 信号基础上做互动判断。
P5instagram-profile-setup落地资料方案和编辑计划。
P6instagram-content-publish落地草稿、发布计划和状态查询计划。
P7instagram-warmup-orchestrator具体能力稳定后做总编排。
P8instagram-official-api第一期不实现，后续专业账号路线再接。

汇报结论：当前设计的核心取舍是“业务 skill 计划化、执行能力 provider 化、跨底座连接协议化”。这能先跑通 TS 插件底座和 MCP connector 路线，同时为 Python agent 通过 protocol 层复用同一套能力留下清晰落点。
